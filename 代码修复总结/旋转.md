# SNN 项目 Hadamard 相关代码修改总结

## 1. 修改目标

本次对话中，Hadamard 相关修改主要围绕两个问题：

1. **确保 GPU 上真正使用 `fast-hadamard-transform` CUDA 实现，而不是静默退回纯 PyTorch 实现；**
2. **降低 BF16 下在线 Hadamard Rotation 的数值误差，重点提高 R3 和 R4 的计算精度。**

其中精度修改是本次最重要的部分。

## 2. Fast Hadamard backend 的最终实现

文件：

```text
snn2/hadamard.py
```

当前 `_fast_fht()`：

```python
def _fast_fht(x: torch.Tensor) -> torch.Tensor:
    if not x.is_cuda:
        return _pure_fht(x, normalized=True)

    try:
        from fast_hadamard_transform import hadamard_transform
    except ImportError as exc:
        raise RuntimeError(
            "CUDA Hadamard requires fast-hadamard-transform. "
            "Install the local package with: "
            "python -m pip install -e ./fast-hadamard-transform --no-build-isolation"
        ) from exc

    try:
        return hadamard_transform(
            x.contiguous(),
            scale=1.0 / math.sqrt(x.shape[-1]),
        )
    except RuntimeError as exc:
        raise RuntimeError(
            "fast-hadamard-transform failed on CUDA; "
            "refusing to silently fall back to the PyTorch implementation."
        ) from exc
```

最终行为：

```text
CPU tensor
    ↓
_pure_fht()

CUDA tensor
    ↓
fast_hadamard_transform.hadamard_transform()
```

CUDA 路径如果 import 或 kernel 执行失败，会直接报错，**不再允许 silent fallback**。这样可以避免正式 GPU 实验看似运行正常、实际上没有走 Fast Hadamard CUDA kernel。

## 4. Hadamard 的结构化实现

调用链：

```text
random_hadamard
        ↓
structured_hadamard
        ↓
_fast_fht
        ↓
fast_hadamard_transform.hadamard_transform
```

对于 2 的幂维度，直接使用 Fast Hadamard。

对于：

```text
12 × 2^m
28 × 2^m
```

形式的维度，使用结构化分解：

```text
大的 2^m 部分
    ↓
Fast Hadamard CUDA kernel

小的 K=12 / K=28 部分
    ↓
Paley Hadamard + torch.einsum
```

例如 Qwen3-1.7B 的部分 R4 intermediate dimension：

```text
6144 = 12 × 512
```

其中大规模 512 维部分由 Fast Hadamard CUDA kernel 计算。

## 5. Randomized Hadamard 的 sign-order 未修改

当前定义：

```python
def random_hadamard(x, spec, transpose=False):
    signs = spec.signs.to(
        device=x.device,
        dtype=x.dtype,
    )

    # Q = H diag(sign).
    # xQ applies H first;
    # xQ^T applies diag(sign) first.
    if transpose:
        return structured_hadamard(
            x * signs,
            spec.factor_k,
            transpose=True,
        )

    return (
        structured_hadamard(
            x,
            spec.factor_k,
            transpose=False,
        )
        * signs
    )
```

本次排查确认该 sign-order 与 transpose 使用方式内部一致，因此没有因为 regression error 去修改符号顺序。

# 6. 精度修改：核心部分

## 6.1 问题背景

模型主体使用：

```text
bfloat16
```

最初在线 R3 / R4 Hadamard 直接对 BF16 tensor 执行：

```python
random_hadamard(x, spec)
```

Hadamard transform 包含大量加法、减法和归一化。直接在 BF16 中反复执行会引入更明显的 rounding error。

因此最终采用：

```text
BF16 activation
    ↓
临时转 FP32
    ↓
执行 Hadamard
    ↓
cast 回原始 dtype
    ↓
继续正常 BF16 forward
```

这只提高 Hadamard 计算本身的精度，不把整个模型改成 FP32。

# 7. R3 在线 Hadamard：Q/K 改为 FP32

文件：

```text
snn2/model_integration.py
```

R3 位于 Attention 的 Q/K 在 RoPE 之后、attention score 之前。

### 修改前

```python
if r3 is not None:
    query = random_hadamard(query, r3)
    key = random_hadamard(key, r3)
```

如果 `query/key` 是 BF16，则 Hadamard 也直接使用 BF16。

### 修改后

当前代码：

```python
if r3 is not None:
    query_dtype = query.dtype
    key_dtype = key.dtype

    query = random_hadamard(
        query.float(),
        r3,
    ).to(query_dtype)

    key = random_hadamard(
        key.float(),
        r3,
    ).to(key_dtype)
```

计算过程：

```text
query BF16
    ↓ .float()
query FP32
    ↓
R3 Hadamard in FP32
    ↓ .to(query_dtype)
query BF16

key BF16
    ↓ .float()
key FP32
    ↓
R3 Hadamard in FP32
    ↓ .to(key_dtype)
key BF16
```

等价于：

$$
Q_{\mathrm{BF16}}
\rightarrow
Q_{\mathrm{FP32}}
\rightarrow
QH_{\mathrm{FP32}}
\rightarrow
QH_{\mathrm{BF16}}
$$

以及：

$$
K_{\mathrm{BF16}}
\rightarrow
K_{\mathrm{FP32}}
\rightarrow
KH_{\mathrm{FP32}}
\rightarrow
KH_{\mathrm{BF16}}.
$$

### 修改原因

R3 的误差会继续进入：

$$
QK^\top
$$

因此 Q/K 上的 Hadamard rounding error 可能被 attention score 放大或逐层累积。将 R3 提升到 FP32 是降低 Rotation 数值误差的关键修改之一。

# 8. R4 在线 Hadamard：MLP product 改为 FP32

文件：

```text
snn2/model_integration.py
```

位置：

```text
gate = SiLU(gate_proj(x))
up   = up_proj(x)

product = gate * up
         ↓
       R4
         ↓
     down_proj
```

### 修改前

```python
product = gate * up

if r4 is not None:
    product = random_hadamard(
        product,
        r4,
    )
```

### 修改后

当前代码：

```python
product = gate * up

if r4 is not None:
    product_dtype = product.dtype

    product = random_hadamard(
        product.float(),
        r4,
    ).to(product_dtype)
```

计算过程：

```text
product BF16
    ↓ .float()
product FP32
    ↓
R4 Hadamard in FP32
    ↓ .to(product_dtype)
product BF16
    ↓
down_proj
```

即：

$$
x_{\mathrm{product}}^{BF16}
\rightarrow
x_{\mathrm{product}}^{FP32}
\rightarrow
x_{\mathrm{product}}^{FP32}R_4
\rightarrow
x_{\mathrm{product}}^{BF16}R_4.
$$

R4 的 intermediate dimension 较大，例如：

```text
6144 = 12 × 512
```

大量 add/sub 在 BF16 中容易累积误差，因此同样提升到 FP32。

# 9. Offline / fused Hadamard 的精度

文件：

```text
snn2/hadamard.py
```

当前 `transform_weight_right()`：

```python
def transform_weight_right(
    weight: torch.Tensor,
    spec: HadamardSpec,
    device: str,
) -> torch.Tensor:
    original_device, original_dtype = (
        weight.device,
        weight.dtype,
    )

    work = weight.to(
        device=device,
        dtype=torch.float32,
    )

    transformed = random_hadamard(
        work,
        spec,
    )

    return transformed.to(
        device=original_device,
        dtype=original_dtype,
    )
```

所以 offline/fused Rotation 采用：

```text
原始权重 dtype
    ↓
FP32 temporary tensor
    ↓
Hadamard in FP32
    ↓
cast 回原始权重 dtype
```

R1、R2、R4 inverse 的主要离线 Hadamard 权重变换都遵循这一策略。

R2 的 value bias 和 `o_proj` 输入权重 Rotation 也显式使用 FP32 temporary tensor 后再 cast 回原 dtype。

# 10. 为什么没有改成 FP64

排查时参考过 PrefixQuant：

- 部分 offline dense rotation 使用 FP64 矩阵乘法；
- 在线 Q/K Hadamard 使用 FP32 后再 cast 回原 dtype。

本项目最终没有把 Fast Hadamard 全部改成 FP64，原因是：

1. 正式 Rotation 依赖 `fast-hadamard-transform` CUDA kernel；
2. 当前 GPU FHT 路径适合实际 FP16/BF16/FP32 使用；
3. 在线 R3/R4 提升到 FP32 已能显著降低 BF16 FHT rounding error；
4. Hadamard 后仍要回到 BF16 模型 forward；
5. 没必要为了 regression 把整个模型或整个 FHT 计算改成 FP64。

最终策略：

```text
模型正常存储 / forward:
BF16

关键 Hadamard transform:
FP32

Hadamard 输出:
cast 回原始 BF16
```

# 12. 为什么要保存原 dtype 再 cast 回去

R3：

```python
query_dtype = query.dtype
key_dtype = key.dtype
```

R4：

```python
product_dtype = product.dtype
```

目的是让：

```text
Hadamard 内部计算精度
```

与：

```text
模型后续 forward dtype
```

解耦。

例如模型为 BF16：

```text
Q/K/product
    ↓
临时 FP32 做 Hadamard
    ↓
恢复 BF16
    ↓
后续 attention / MLP 仍保持原实验 dtype
```

因此修改的是 Rotation transform 的数值精度，而不是整个训练/推理 dtype 协议。

# 13. 与 Rotation regression 的关系

最初 Rotation regression 曾出现：

```text
relative_l2_error ≈ 0.259
```

约 25.9%。

后来同时完成两类关键修复：

1. Base 与 Rotated 两侧统一使用相同的 SNN2 forward integration，使主要差异只剩 Rotation；
2. R3 / R4 在线 Hadamard 从 BF16 改为 FP32 计算后再 cast 回原 dtype。

之后 Qwen3-1.7B regression 降至：

```text
relative_l2_error
=
0.007705130877581711
```

约 0.7705%。

需要注意：

> 25.9% → 0.77% 的改善不能全部归因于 FP32 Hadamard，因为 forward-path 一致性也同时被修正。

但 R3 / R4 的 FP32 Hadamard 是降低 BF16 Rotation numerical error 的重要精度修复。

# 14. 最终 Hadamard 精度策略汇总

| 场景                               | 输入通常 dtype                | Hadamard 计算 dtype     | 输出 dtype        |
| ---------------------------------- | ----------------------------- | ----------------------- | ----------------- |
| Offline R1 weight rotation         | BF16                          | FP32                    | BF16              |
| Offline R2 weight rotation         | BF16                          | FP32                    | BF16              |
| Offline R4 inverse weight rotation | BF16                          | FP32                    | BF16              |
| Online R3 Query                    | BF16                          | **FP32**                | BF16              |
| Online R3 Key                      | BF16                          | **FP32**                | BF16              |
| Online R4 MLP product              | BF16                          | **FP32**                | BF16              |
| CPU FHT / unit-test path           | input dtype                   | pure PyTorch            | input-compatible  |
| CUDA FHT                           | 当前 Rotation 调用主要为 FP32 | fast-hadamard-transform | caller-controlled |

核心原则：

```text
不要让关键 Hadamard Rotation 直接在 BF16 中完成。

BF16 tensor
    ↓
FP32 Hadamard
    ↓
cast back to BF16
```

# 15. 最终状态

```text
1. CUDA 正式路径使用 fast-hadamard-transform。

2. CUDA kernel 缺失或失败时 hard fail，
   不允许 silent fallback。

3. fast-hadamard-transform submodule revision
   固定为 e7706faf8d1c3b9f241e36860640ad1dac644ede。

4. Randomized Hadamard 的 sign-order 保持不变。

5. Offline fused weight Hadamard 使用 FP32 temporary tensor。

6. Online R3 Q/K：
   BF16 → FP32 → Hadamard → BF16。

7. Online R4 product：
   BF16 → FP32 → Hadamard → BF16。

8. 不把整个模型或 Fast Hadamard 改成 FP64。
```

其中第 6、7 点是本次为了 Rotation regression 精度重点完成的修改。
